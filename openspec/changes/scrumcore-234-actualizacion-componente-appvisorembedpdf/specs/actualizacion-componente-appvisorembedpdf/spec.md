### Requirement: Detalle funcional Jira
El sistema SHALL considerar las reglas detalladas del ticket.

#### Scenario: Reglas del ticket
- PROMPT ARQUITECTÓNICO (ENTERPRISE) — Auto‑Fit determinístico en AppVisorEmbedPdf (sin heurísticas, sin romper zoom/scroll/viewport)
-   Rol esperado  Arquitecto frontend senior (React 19, TypeScript estricto, EmbedPDF, UX enterprise, estabilidad runtime, testing)
-   Objetivo  Implementar “Auto‑Fit inteligente” pero determinístico en el visor EmbedPDF, sin modificar backend y sin comprometer la funcionalidad actual:
- Ajustar automáticamente escala/centrado al cargar el documento y cuando cambie el viewport.
- 
- Basarse únicamente en datos confiables del engine (tamaño real de página y rotación metadata).
- 
- No aplicar “auto‑rotate por contenido” (OCR/imagen) para evitar falsos positivos.
- 
- No romper interacciones existentes: zoom manual, scroll, thumbnails, rotate manual, anotaciones/firma, cancelación/latest‑wins y loaders actuales.
- 
-   IMPORTANTE — Este ticket NO debe
- Cambiar backend/endpoints.
- 
- Introducir heurísticas de detección por OCR/imagen/ML.
- 
- Persistir URLs temporales/tokens.
- 
- Romper consumidores legacy ni el flujo actual de carga/cancelación.
- 
- Cambiar el set de plugins o su orden sin justificación y pruebas.
- 
- Forzar auto‑fit continuamente (no “pelear” con el usuario).
- 
-   IMPORTANTE — Este ticket SÍ debe
- Implementar auto‑fit determinístico por página y por viewport.
- 
- Respetar rotación real (metadata) que reporta el engine.
- 
- Mantener UX estable: “no saltos”, no flicker, no resets inesperados de zoom.
- 
- Incluir toggle de modo y reglas claras de cuándo auto‑fit aplica.
- 
- Incluir documentación enterprise + pruebas.
- 
-   Contexto del proyecto (actual)
- AppVisorEmbedPdf abre documentos PDF vía engine EmbedPDF y plugins (viewport/scroll/render/zoom/rotate/thumbnail/print/export/annotation/signature).
- 
- Existe control de concurrencia (cancel chain / latest‑wins) y overlay/skeleton.
- 
- Rotación manual existe vía plugin Rotate.
- 
-   Definición del problema  Algunos PDFs llegan escaneados/digitalizados con orientación incómoda (portrait/landscape/rotación metadata), y el usuario necesita que el documento:
- se ajuste al viewport (fit‑to‑width o fit‑to‑page según política),
- 
- quede centrado,
- 
- no rompa zoom manual ni scroll actual.
- 
-   Alcance funcional (lo que se implementa)
- Auto‑Fit determinístico (sin auto‑rotate por contenido)
- 
- En “document ready” (después de openDocumentUrl + handshake ready):
- calcular fitScale usando dimensiones de la página actual y el viewport.
- 
- En resize del visor:
- si el usuario NO ha hecho zoom manual desde la última carga → recalcular y aplicar fit.
- 
- si el usuario ya tocó zoom → no tocar (hasta que el usuario reactive “Smart Fit”).
- 
- Reglas de convivencia con zoom manual (no intrusivo)
- 
- Estado interno:
- smartFitEnabled: boolean (default ON al cargar un doc).
- 
- userZoomDirty: boolean (se vuelve true si el usuario hace zoom manual, wheel/pinch/buttons).
- 
- Regla:
- Auto‑fit solo si smartFitEnabled && !userZoomDirty.
- 
- UI:
- Botón/toggle “Smart Fit” (ON/OFF) en toolbar del visor.
- 
- Acción “Fit to width” / “Fit to page” (si el producto lo quiere) como modos:
- fitMode: "width" | "page" (default: width).
- 
- Rotación
- 
- Respetar rotación metadata real del PDF que expone el engine.
- 
- No rotar automáticamente “porque parece landscape”.
- 
- Si el usuario rota manualmente (plugin Rotate):
- marcar userZoomDirty=true (o una bandera separada userViewportDirty) para no re‑auto‑fit agresivamente, o recalcular fit de forma controlada (definir política explícita).
- 
- Compatibilidad con flujo actual
- 
- No alterar:
- cancelación/latest‑wins,
- 
- overlay/skeleton,
- 
- cierre/abrir documento (maxDocuments),
- 
- plugins existentes.
- 
- Auto‑fit se integra “después del ready”, y debe ser stale‑safe (si cambia de doc mientras calcula, ignorar).
- 
-   Diseño técnico obligatorio
- Punto de integración: AppVisorEmbedPdf (no Workbench).
- 
- Implementación en módulo aislado (para no ensuciar el componente):
- src/app/Components/UI/AppVisorEmbedPdf/autoFit/ (sugerido)
- autoFit.types.ts
- 
- autoFit.math.ts (cálculo scale/offsets)
- 
- useAutoFitController.ts (estado smartFitEnabled/userZoomDirty, handlers)
- 
- autoFit.apply.ts (aplica zoom/centering al engine con guards)
- 
- API mínima interna:
- computeFitScale(pageSize, viewportSize, fitMode): number
- 
- applyAutoFit(engine, { scale, center }): Promise<void>
- 
- markUserZoomDirty() on user zoom events
- 
-   Concurrencia / stale‑ignore (obligatorio)
- Toda aplicación de auto‑fit debe estar ligada a la identidad del documento actual (ej. documentId o loadSeq ya existente).
- 
- Si el documento cambia antes de aplicar el fit → abortar/ignorar (no afectar nuevo doc).
- 
-   Performance (obligatorio)
- Debounce/throttle en resize (p. ej. 50–100ms).
- 
- Evitar loops: aplicar fit no debe disparar eventos que re‑apliquen fit infinitamente.
- 
-   Accesibilidad (obligatorio)
- Toggle “Smart Fit” con aria-pressed.
- 
- Estados anunciables y sin focus traps.
- 
-   Pruebas obligatorias  Unit (math/guards):
- computeFitScale fit‑to‑width y fit‑to‑page.
- 
- No aplica auto‑fit si userZoomDirty=true.
- 
- Stale‑ignore: no aplica si docId/loadSeq cambió.
- 
-   Integración (React):
- Al cargar doc: auto‑fit aplica una vez post‑ready.
- 
- Si usuario hace zoom manual: no vuelve a auto‑fit en resize.
- 
- Si se reactiva Smart Fit: vuelve a aplicar fit.
- 
-   Manual QA (checklist):
- PDF portrait, PDF landscape, PDF con rotación metadata.
- 
- Rotar manualmente + fit.
- 
- Thumbnails/scroll/paginación sin saltos.
- 
- Zoom manual persistente.
