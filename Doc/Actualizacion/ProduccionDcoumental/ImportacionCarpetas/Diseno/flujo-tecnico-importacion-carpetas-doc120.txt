================================================
Estado: implementacion existente; corte de codigo 1a45b891.
Formato: texto UTF-8. Las cajas, flechas y decisiones no requieren Mermaid.

LECTURA Y ALCANCE
----------------
Este documento describe el codigo actual, incluida la preparacion segmentada,
la coordinacion del navegador, persistencia documental V2 y recuperacion.
No describe como implementadas las optimizaciones de metadatos propuestas.
RA y DA son origenes logicos resueltos desde la sesion, no nombres de bases.
HTTP indicado = estado que asigna EstadoHttp al sobre de la aplicacion.
IIS/ASP.NET puede rechazar antes de entrar; ver [15].

  [CAJA]       = clase/metodo real o conjunto explicitamente identificado.
  <decision?> = condicion; SI/NO indican sus salidas.
  -->         = llamada o siguiente paso.
  <--         = respuesta; no significa rollback del efecto anterior.
  E(codigo)   = salida por el traductor comun [15], salvo captura local indicada.
  CAS         = escritura condicionada por revision/estado/identidad de intento.

Para no ocultar condiciones extensas bajo frases como "validar todo", se entrega
el anexo flujo-tecnico-importacion-carpetas-doc120-anexo.txt. Contiene contratos,
despacho real, firmas, condiciones y filtros literales con archivo/linea.
Las ramas SI/NO del mapa deben leerse junto con esos predicados, no sustituirlos.
El anexo incluye tambien capacidades internas y administrativas: su presencia
en codigo no significa que sean botones o pasos del asistente operativo.

4. PREPARACION TRADICIONAL Y REGLAS
---------------------------------
+ CLIENTE action("preparar") ---------------------------------------------+
| request={nivelRef,versionId,raices[],archivos[]}.                          |
| <segmentado disponible, data-preparacion-segmentada=2 Y                  |
|   (archivos>100 O cuerpo supera data-maximo-json)?>                       |
| SI -> [5]. NO -> API.invocar("PrepararPlan",request).                   |
+------------------------------------------------------------------------+
    -> ASMX.PrepararPlan -> EjecutarOperativo -> ServicioPreparacionImportacion
       .Preparar -> CalcularPlan(solicitud,esquemaDoc=1).
    -> CanonizadorManifiestoImportacion.Canonizar:
       IDs cliente/seleccion, pertenencia, nombre/rutas, normalizacion,
       bytes/fecha decimal, duplicados y limites; inventario inmutable.
    -> AdaptadorPerfilImportacionOperativa.Seleccionar(contexto,versionId)
       -> publicacion vigente y hash; ValidadorPerfilImportacion.Validar.
    -> CanonizadorManifiestoImportacion.EvaluarAgrupacion:
       EstrategiaCarpetas=RAIZ_EXPEDIENTE; PoliticaSubcarpetas=INCLUIR|RECHAZAR.
       INCLUIR incorpora archivos descendientes a esa misma raiz/expediente;
       RECHAZAR genera SUBCARPETA_NO_PERMITIDA si ruta tiene mas de2 segmentos.
       No crea expedientes intermedios por cada subdirectorio.
    -> PerfilImportacionCatalogAdapter.ClasificacionOperativa.
    -> CoordinadorProveedorIndices.ResolverOperativo:
       reglas de CAMPO_EXPEDIENTE por raiz; demas reglas por archivo.
       ResolvedorReglasPerfilImportacion: constantes, nombres/extraccion,
       propiedades de expediente y proveedor segun regla publicada.
       Dependencia TRAS_EXPEDIENTE queda tipada como Diferido; no inventa ID.
       Proveedor solo lectura, publicacion/clave/propiedad autorizadas;
       misma version/clave puede compartirse en esa llamada, no cache global.
       MySqlProveedorDatosIndices.ConsultarOperativo -> ConsultarDatos:
       ConexionRef RA|DA segun politica autorizada, tabla/columnas cerradas y
       compatibles con information_schema; clave parametrizada, columna de
       empresa solo si esta configurada, LIMIT2. Cero filas SIN_COINCIDENCIA;
       varias AMBIGUO; tipos/clave invalidos o dependencia caida -> incidencia.
       No afirmar filtro empresarial de datos si el proveedor no lo configura;
       la autorizacion de la fuente sigue siendo obligatoria.
    -> ValidarValoresOperativos: tipos, obligatorios, longitudes, fechas,
       representacion destino, gabinete/indices/tipologia y clasificacion.
       CODIGO <=45 y NOMBRE <=120 en este recorrido; no truncar silenciosamente.
       Extension y MaximoBytesArchivo del perfil generan incidencias.
    -> MySqlImportacionCarpetasRepository.ComprobarCoincidencias:
       actualmente comprobacion TECNICA del codigo/esquema, sin buscar
       candidatos por nombre o CODIGO_UNICO para impedir duplicados.
       PoliticaCoincidencias conserva contrato/valores historicos, pero NO
       activa hoy exclusividad ni reutilizacion de expedientes. ID_EXPEDIENTE
       es la identidad; no se deduce identidad de un texto repetido.
       Fallo de dependencia capturado -> incidencia GLOBAL bloqueante.
    -> EvaluarElegibilidad:
       <incidencia global bloqueante?> SI -> PuedeConfirmar=False.
       <COMPLETO_OBLIGATORIO / LOTE y alguna incidencia bloqueante?>
           SI -> ninguna unidad elegible.
       <COMPLETO_OBLIGATORIO / EXPEDIENTE?>
           cada raiz exige sus archivos sin incidencias bloqueantes.
       <PARCIAL_PERMITIDO / NO_APLICA?>
           raiz sin bloqueo propio y al menos un archivo elegible.
       Otra combinacion -> CONFIGURACION_INVALIDA HTTP400.
    -> Preparar exige reloj UTC; CreadoUtc/ExpiraUtc; GuardarPlan(contexto,plan)
       -> ra_integracion_plan, hash del contenido y revision persistida.
    <-- HTTP200 {planId,revision,planHash,expiraUtc,nivelRef,snapshot,resultado}.
        Puede ser plan BLOQUEADO con incidencias: HTTP200 NO significa elegible.
        No crea lote, expediente ni documento y no recibe bytes PDF.

      identidad,destino,esquema de preparacion,perfil/recursos,UTC.

    + RegistrarPartePreparacion -> Registrar(s): tipo RAICES|ARCHIVOS,
      numero>0, lista correspondiente no vacia y otra vacia,<=100 entradas,
      correlaciones/bytes; AutorizarPreparacion(escritura=True), vigencia y
      publicacion. RegistrarParte con revision/numero/hash/contenido.
      Repeticion compatible conserva parte; contenido distinto/conflicto ->409.
    + ConsultarPreparacionPlan -> Consultar(s): por preparacionId O

      IniciarLecturasPreparacion; sello catalogos antes/despues debe coincidir;

      persiste fragmentos y sello bajo revision.
    + SellarPreparacionPlan -> Sellar(s): claveCierre coincide; SELLADA devuelve
      revision existente, no otro plan. Si BORRADOR: vigencia, partes completas
      VALIDADA, sellos actuales, canonizacion global, reconstruir fragmentos,
      deduplicar incidencias y evaluar elegibilidad global. SellarPreparacion

        Fallo incierto -> pausa + consulta del mismo borrador; sin retry ciego.

6. CONFIRMACION DEL PLAN Y CREACION DEL LOTE
-----------------------------------------
+ Cliente action("confirmar" | "confirmar-importar") ----------------------+
| operation.referenciaConfirmacion -> {planId,revisionEsperada,             |
| planHashEsperado,claveConfirmacion}; recuerda plan pendiente antes de POST.|
+------------------------------------------------------------------------+
    -> ASMX.ConfirmarPlan -> ServicioRecepcionImportacion.Confirmar(s)
       IDs/revision/hash64hex/clave validos; identidad actual ->
       ObtenerContextoPlan(identidad,planId) -> propietario/empresa ->
       ResolverDestino(CONFIRMAR) -> sello/ruta -> ObtenerPlan -> hash ->
       AutorizarRecursos(snapshot confirmado).
    <plan.Estado=CONFIRMADO?>
    SI -> no vuelve a seleccionar perfil ni aplicar expiracion; repositorio
          determina idempotencia/conflicto bajo transaccion.
    NO -> exige REVISABLE,revision exacta,PuedeConfirmar,UTC no vencido;
          canoniza inventario; misma publicacion; comprueba incidencias actuales
          para unidades elegibles. Fallo ->409 con causa segura del diagnostico.
    -> MySqlImportacionCarpetasRepository.ConfirmarPlan(...):
       transaccion, bloquear plan, unicidad/idempotencia por plan/clave/hash,
       insertar lote RECIBIENDO, raices y archivos del inventario ORIGINAL,
       estados de recursos segun elegibilidad, valores previstos, referencias
       y evento; confirmar plan. VerificarPublicacion se reejecuta bajo tx.
       Incluye recursos rechazados; no desaparecen del total original.
    <-- HTTP200 ConfirmacionImportacionResultado {loteId,planId,nivelRef,
        estado,revision,totalRaices,totalArchivos,totalBytes}.
    <se pierde respuesta?>
    SI -> confirmacionIncierta; ConsultarConfirmacionLote({planId}) [12].
          No reenviar confirmacion con otra clave para adivinar el resultado.
    NO -> conserva ultimo lote; consulta seguimiento.
          Si accion fue confirmar-importar y la consulta termina bien -> [7].

7. COORDINACION CLIENTE: UNA OPERACION EN VUELO
--------------------------------------------
+ ImportacionCarpetas.crearCoordinacion(options) --------------------------+
| Consentimiento efimero; no cola ejecutable persistida ni worker servidor.|
| limites:10000 recursos,400 paginas por enumeracion,10000 lecturas/efectos.|
| readAll: ConsultarLote -> TODAS paginas RAICES/ARCHIVOS sin filtros,25     |
| filas (o menor maximo servidor) -> ConsultarLote final misma revision.    |
| Valida IDs,cantidades,pertenencia,ambito y resultados ya confirmados.      |
+------------------------------------------------------------------------+
    -> cycle(token,snapshot)
       <cerrado,token/contexto cambio o pausa?> SI -> no despachar siguiente.
       <lote COMPLETADO?> SI -> estado cliente complete.
       <detencion,activo,incertidumbre,DETENIDO/FALLIDO/PENDIENTE_VERIFICACION
         o recursos CREANDO/EN_CURSO/INCIERTO/RECIBIENDO?>
           SI -> blocked; no elige efecto ni reanuda automaticamente.
       NO -> choose(snapshot), en este ORDEN:
         1) primer archivo elegible PENDIENTE/NO_INICIADO -> RECEPCION [8].
         2) primera raiz PENDIENTE con recepcionListaParaCrear -> CREAR [9].
         3) archivo recibido con padre confirmado y valores sin fijar -> [10].
         4) archivo recibido con valores fijados y padre confirmado -> [11].
       <no hay accion?> -> paused/SIN_AVANCE_DISPONIBLE.
       <operacion ya confirmada o fallida en esta coordinacion?>
           -> blocked/RESULTADO_PENDIENTE_LECTURA; no replay.
       <RECEPCION sin File original valido?> -> needs-original/ORIGINAL_REQUERIDO.
       -> ejecutar UNA solicitud -> confirm(op,result,snapshot).
       <acuse no corresponde al lote/recurso/fase/IDs/estado?>
           -> error RESPUESTA_INVALIDA, resultadoIncierto=True; detener.
       SI corresponde -> guarda resultado confirmado -> lectura posterior:
         readFocal si data-consulta-focal=1 y hay snapshot previo:
           ConsultarRecursoLote -> reemplazar recurso/padre, revisiones no
           retroceden; huellaRecursos del servidor igual a SHA256 cliente;
           comprobar progreso. Otro recurso cambiado -> conflicto, no ignorarlo.
         Si no capacidad focal -> readAll con revision consistente.
       <lectura posterior falla?> -> conservar acuse, marcar consulta pendiente;
         no declarar fallido lo ya confirmado ni repetir escritor.
       -> ceder al navegador -> elegir siguiente. No almacenar en paralelo.

Pausar: no despacha otra accion; espera la respuesta en vuelo.
Cerrar: invalida generacion, descarta File/estado/URLs; cerrar API puede abortar
espera HTTP, pero NO revierte lo ya ejecutado en servidor.
Continuar: relee estado y exige consentimiento; no infiere exito por tiempo.
Contadores: recibidos / expedientes / datos fijados / guardados, por estado e ID
confirmados. Bytes de xhr.upload NO equivalen a recepcion ni guardado.
Filtros de pantalla no reducen la enumeracion completa de la coordinacion.

  Limpieza/retencion: ServicioConsultaImportacion.DiagnosticarRetencion y

  ARCHIVO_RECHAZADO                                            -> HTTP422
