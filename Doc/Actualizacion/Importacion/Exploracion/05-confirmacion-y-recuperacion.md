## RESTRICCIONES CRÍTICAS

- Mantener la sesión y empresa como autoridad. El navegador envía referencias, nunca un servidor, base o cadena de conexión elegidos libremente.
- No imprimir ni persistir credenciales, cookies, tokens o cadenas de conexión en código, documentación o evidencias. Usar secretos efímeros durante pruebas y configuración protegida para la cuenta del servidor.
- No modificar AlmacenamientoDocumentoProduccionDocumental ni SII para resolver la carga tabular. Preservar los contratos de los consumidores existentes.
- CSV, migración entre gabinetes, omisión de duplicados y actualización automática por coincidencia de clave están fuera de alcance.
- El agente genera los cambios SQL en archivos e indica su ejecución manual por el usuario. No debe ejecutar SQL modificador de esquema, datos o permisos ni aplicar archivos SQL directa o indirectamente. La comprobación posterior utiliza exclusivamente SELECT después de la confirmación de ejecución manual.
- Conservar los cambios ajenos presentes en el repositorio local y agrupar las entregas conforme al flujo del cambio.

## IMPLEMENTACIÓN DE ESTA FASE

1. Implementar Confirmar y ConsultarResultado. Verificar permiso vigente, usuario/empresa, ID y correspondencia de la petición con el archivo y la configuración registrados. Cuando ese ID ya esté CONFIRMADA, devolver su resultado persistido tras comprobar la identidad y el contenido de la petición. Ese resultado describe la ejecución histórica, aunque después cambien la plantilla, el esquema o los límites.
2. Para una carga pendiente, verificar archivo/hash, revisión y huella de plantilla, esquema, modo y límites vigentes. Adquirir el bloqueo cooperativo por destino y bloquear y releer el registro de ejecución en la conexión dedicada. Comprobar otra vez si una petición concurrente ya lo confirmó antes de realizar efectos. Para crear, distinguir la estructura propia identificada por ID de carga de una tabla ajena.
3. Para agregar, revisar de nuevo los conflictos y ejecutar INSERT parametrizados en agrupaciones acotadas dentro de una transacción.
4. Para reemplazar, ejecutar DELETE e INSERT del contenido autorizado dentro de la misma transacción InnoDB. Mantener el índice único y aplicar el filtro empresarial cuando corresponda.
5. Guardar CONFIRMADA y las filas efectivas en esa misma transacción. Ante fallo conocido, revertir toda la carga y registrar la incidencia de forma consistente. Una respuesta incierta conserva su ID para consulta antes de repetir.
6. Implementar en el código del módulo la fase operativa de crear con el índice único y el ID de carga en el comentario de la tabla. Una repetición comprueba procedencia y huella de esquema antes de continuar. Un destino ajeno existente produce conflicto. El agente entrega los cambios SQL de instalación o adecuación como archivos para ejecución manual y revisión posterior mediante SELECT.
7. Implementar el modo SQL estricto de la conexión del módulo y validar la clave requerida/NOT NULL. La adecuación de índices de tablas históricas se entrega como archivo SQL específico, después del diagnóstico de datos, para ejecución manual y comprobación SELECT posterior.
8. Implementar pruebas de concurrencia que distingan la serialización del módulo y la protección permanente del índice UNIQUE frente a otros escritores.

## CRITERIOS DE ACEPTACIÓN

- Los tres modos realizan las escrituras autorizadas y conservan la semántica acordada de duplicados.
- Un fallo durante reemplazar conserva los datos anteriores tras rollback.
- Dos confirmaciones del mismo ID producen una única carga efectiva.
- Una respuesta perdida se resuelve mediante consulta del registro y el estado estructural pertinente.
- Una carrera sobre la misma clave termina con la protección del índice único y el rollback de la carga en conflicto.
- La creación recuperable conserva su identidad incluso cuando falla la carga de filas posterior.
- La compilación y pruebas focales acreditan transacción, resultados y errores.
